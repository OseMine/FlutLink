## Befunde

### B1 — Bug: Erneutes Hinzufügen des aktiven Kontos schaltet still auf ein anderes Konto um

**Datei/Funktion:** `src-tauri/src/commands.rs` → `account_add` (Zeilen 47–61) i. V. m. `src-tauri/src/state.rs` → `upsert` (Zeilen 148–156) und `current` (Zeilen 138–145)

`has_accounts` wird **vor** dem `upsert` aus der Snapshot-Liste berechnet. Wenn
ein bereits vorhandenes Konto erneut hinzugefügt wird (z. B. Token-Erneuerung),
gilt `has_accounts == true` → `is_active: false`. `upsert` entfernt danach den
bestehenden Eintrag (gleiche `instance_url` + `username`) und hängt den neuen
mit `is_active=false` an. Ergebnis: **kein** Konto ist mehr als aktiv markiert,
und `current()` fällt auf `guard.first()` zurück — das kann ein *anderes*
Konto sein. Der Nutzer denkt, er erneuert sein aktives Konto, und die App
arbeitet still auf einem anderen Konto weiter.

Verifiziert mit Replikation der exakten Logik (siehe Abschnitt „Verifikation"):

```
snapshot after re-adding account A:
  B active=false
  A active=false
current() => B
RESULT: BUG CONFIRMED — active account silently switched to B
```

**Fix-Vorschlag:** `is_active` nach dem `upsert` bestimmen (bzw. `upsert`
so ändern, dass ein ersetztes Konto den `is_active`-Status des entfernten
Eintrags übernimmt, falls kein anderes aktiv ist).

### B2 — Bug: Theme „System Default" folgt nie dem Betriebssystem

**Datei/Funktion:** `src/App.vue` → `resolveTheme` (Zeilen 37–39) und der
`matchMedia`-Listener (Zeilen 49–51)

```ts
function resolveTheme() {
  resolvedTheme.value = ui.theme === "system" ? "operationflut" : ui.theme;
}
```

`"system"` wird **immer** auf `"operationflut"` abgebildet, nie auf
`"midnight"`. Der Listener lauscht zwar auf `prefers-color-scheme: light`,
das Ergebnis wird aber ignoriert. Der i18n-Text `systemThemeNote`
(„System Default follows your operating system") verspricht mehr, als der
Code liefert. Ein Nutzer, der „System Default" wählt, bekommt immer das
OperationFlut-Theme.

**Fix-Vorschlag:** `matchMedia("(prefers-color-scheme: dark)").matches`
auswerten und bei `system` auf `"midnight"` abbilden, wenn das OS dunkel
präferiert (bzw. Option entfernen, falls bewusst nur dunkel).

### B3 — Feature-Lücke: Share-Erstellung während Admin-Impersonation zielt auf das falsche Konto

**Datei/Funktion:** `src-tauri/src/commands.rs` → `webdav_create_share` (Zeilen 264–268), `src-tauri/src/nextcloud/ocs.rs` → `create_share` (Zeilen 231–251), `src/components/FileExplorer.vue` → `createLink` (Zeilen 31–41)

`webdav_create_share` nimmt kein `target_user`. Wenn ein Admin im
Impersonations-Modus (Browsing der Dateien von Benutzer B) einen Link
erstellt, wird `entry.path` (relativ zu B's Dateiroot) gegen das **Admin**-Konto
an die OCS-Share-API geschickt. Das ergibt entweder einen 404/Fehler oder —
schlimmer — einen falschen Link auf einen gleichnamigen Pfad im Admin-Account.
`webdav_list` unterstützt `target_user` bereits, `webdav_create_share` nicht.

**Fix-Vorschlag:** `target_user` als Parameter ergänzen und beim Share-Aufruf
die Impersonation (bzw. den richtigen Account) verwenden.

### B4 — Feature-Lücke: Benutzerliste ist hart auf 200 limitiert (keine Pagination)

### B8 — Bug (Minor): Nicht-aktives Konto nach Re-Add wird in der UI nicht korrekt dargestellt

**Datei/Funktion:** `src/stores/accounts.ts` → `add` (Zeilen 47–61) und `load` (Zeilen 21–33)

In Kombination mit B1: `add()` pusht das Konto nur, wenn der Username neu ist
(`if (!accounts.value.some(...))`), und setzt `active` nur bei
`account.isActive`. Nach B1-Szenario bleibt das alte `active`-Objekt stehen,
während das Backend ein anderes Konto liefert — Store und Backend laufen
auseinander. B1 beheben; danach `add()` um einen Reload der Account-Liste
ergänzen.

### B9 — Robustheit: WebDAV-Liste erkennt stilles Ignorieren der Impersonation nicht

**Datei/Funktion:** `src-tauri/src/nextcloud/webdav.rs` → `list` (Zeilen 39–41, 46–50) und `relative_path` (Zeilen 372–383)

Wenn die `Impersonate-User`-Unterstützung auf dem Server fehlt (App
`impersonate` nicht installiert/aktiviert), ignoriert Nextcloud den Header und
liefert die Dateien des **Admin**-Accounts. `relative_path` findet dann die
`base_path` nicht im href, fällt auf den rohen href zurück und erzeugt
kaputte Pfade (z. B. `/remote.php/dav/files/admin/...`), die im Frontend
als normale Einträge erscheinen. Es gibt keinen Abgleich zwischen
angefordertem `effective_user` und dem tatsächlichen href-Namespace.

**Fix-Vorschlag:** Nach dem Parse prüfen, ob alle hrefs unter der erwarteten
`base_path` liegen; andernfalls `AppError` mit klarer Meldung („Impersonation
vom Server nicht unterstützt").

### B11 — Verbesserung (Minor): Leere Verzeichnisse werden remote nicht gelöscht; lokale Ordner ohne Dateien nie erstellt

**Datei/Funktion:** `src-tauri/src/sync.rs` → `decide` (Zeilen 278–281), `walk_local` (Zeilen 126–168), `plan_ops` (Zeilen 302–348)

### B13 — CI/Security: `opencode.yml` erlaubt Code-Ausführung aus Kommentaren mit Schreibzugriff

**Datei/Funktion:** `.github/workflows/opencode.yml` (Zeilen 34–112)

Der Workflow triggert bei jedem Issue/PR-Kommentar mit `/oc` oder
`/opencode` von Nutzern mit Schreibzugriff und gibt der Agent-Session
`contents: write`, `pull-requests: write`, `issues: write` **und**
`id-token: write`. Der Kommentartext wird ungefiltert in den Prompt injiziert
(„Handle the triggering comment"). Damit kann jeder Write-Collaborator über
Prompt-Injection beliebigen Code in einer Umgebung mit Repository-Write-Rechten
ausführen. Zudem ist `id-token: write` unnötig (kein OIDC-Verbrauch) und
vergrößert die Angriffsfläche.

**Empfehlungen:** `id-token: write` entfernen; den Prompt so umformulieren,
dass der Kommentar als *Aufgabenbeschreibung*, nicht als Instruktion
behandelt wird; Rechte so eng wie möglich halten; den Diff der Agent-Änderungen
vor dem Auto-Commit auf verdächtige Muster prüfen (z. B. Secrets-Exfiltration).

### B14 — Robustheit: Kein CSP in `tauri.conf.json`

**Datei/Funktion:** `src-tauri/tauri.conf.json` → `app.security.csp` (Zeile 23)

`"csp": null` deaktiviert die Content Security Policy. Die App lädt nur
lokale Assets, aber Tauri v2 empfiehlt eine CSP. Ein `default-src 'self'`
(bzw. `script-src 'self'`) wäre ein sinnvoller Mindestschutz, falls je
Remote-Inhalte (z. B. SVG/Bilder aus WebDAV) gerendert werden.

### B17 — Robustheit: `keyring`-Ausfall macht die App auf Linux ohne Secret-Service unbenutzbar

**Datei/Funktion:** `src-tauri/src/accounts.rs` → `save_token` (Zeilen 20–26), `load_accounts` (Zeilen 54–68)

Auf Linux-Desktops ohne laufenden Secret-Service (z. B. minimal Window
Manager, headless CI) schlägt `save_token` fehl → `account_add` bricht ab;
`load_accounts` überspringt stumm alle Konten ohne Token, d. h. die gesamte
Account-Liste verschwindet temporär. README erwähnt die Keychain-Persistenz,
aber ein erklärender Fehlertext bzw. ein Dokumentationshinweis für
Linux-Nutzer (gnome-keyring/kwallet nötig) fehlt.

### B18 — Robustheit: Reste von `.tmp`-Dateien werden nicht aufgeräumt

**Datei/Funktion:** `src-tauri/src/nextcloud/webdav.rs` → `get_file` (Zeilen 147–159), `tmp_path` (Zeilen 241–248)

Bricht ein Download nach `File::create(&tmp)` ab (Stream-Fehler), wird die
`.flutlink-<pid>.tmp`-Datei nicht gelöscht (nur im Fehlerfall von `rename`
aufgeräumt). Die Datei ist zwar versteckt und wird von `should_skip_name`
übersprungen, sammelt sich aber über die Zeit an. Beim Stream-Fehler ebenfalls
`remove_file(&tmp)` ausführen.
