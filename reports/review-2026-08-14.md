## Neue Befunde (Lauf 2026-08-14)

### F1 — [Bug, Blockierer] `admin_edit_user` lehnt Key `enabled` ab, Button im AdminPanel schlägt immer fehl

- **Datei/Funktion:** `src/components/AdminPanel.vue:143-145` (`toggleEnabled` →
  `api.adminEditUser(selected.value.id, "enabled", …)`) vs.
  `src-tauri/src/commands.rs:550-570` (`ADMIN_EDIT_KEYS`-Whitelist ohne
  `enabled` → `AppError` „Editing key 'enabled' is not allowed").
- **Problem:** Der „Aktivieren/Deaktivieren"-Button (Zeile 306) im AdminPanel
  kann prinzipiell nie erfolgreich sein. Backend-Whitelist kennt nur
  `displayname, email, quota, password, language, locale`.
- **Fix-Vorschlag:** Entweder `enabled` in `ADMIN_EDIT_KEYS` aufnehmen
  (`ocs::update_user` unterstützt `enabled` seit Nextcloud 25) oder den Button
  aus dem UI entfernen. Nicht beides divergieren lassen.

### F2 — [Bug, Blockierer] Total-Timeout von 60 s (HTTP-Client) bricht große WebDAV-Transfers ab; 30 s im Updater

- **Datei/Funktion:** `src-tauri/src/state.rs:112-113`
  (`Client::builder().timeout(Duration::from_secs(60))`) und
  `src-tauri/src/updater.rs:526-527` (`.timeout(…30…)`).
- **Problem:** reqwest `.timeout()` ist ein **Total-Timeout über die gesamte
  Transaktion inkl. Body**. Alle WebDAV-Dateioperationen (Upload/Download via
  `webdav::put_file`/`get_file`, Sync-Engine, Datei-Commands) laufen über den
  60-s-Client → Uploads/Downloads von Dateien, die länger als 60 s brauchen,
  brechen ab. Der Updater-Download von >30 s (typisch bei 100+ MB-Installern)
  bricht ab; die partielle Datei bleibt liegen (siehe F3).
- **Fix-Vorschlag:** `connect_timeout` + `read_timeout` (reqwest 0.13) statt
  Gesamt-`timeout`, oder Timeout nur für Nicht-Streaming-Requests setzen.
  Mindestens separat `read_timeout` für Datei-Transfers verwenden.

### F3 — [Bug, minor] Updater räumt partielle Downloads bei Fehlern nicht auf

- **Datei/Funktion:** `src-tauri/src/updater.rs` `download_update` (Stream-
  Schleife um Zeile 260-283).
- **Problem:** Bricht der Stream ab (vgl. F2), bleibt die `.part`/Tmp-Datei im
  Cache liegen; beim nächsten Versuch wird neu begonnen. Analog zu B18 (war für
  `get_file_as` behoben, hier nicht).
- **Fix-Vorschlag:** Im Fehlerpfad die partielle Datei löschen (wie
  `get_file_as`).

### F4 — [Bug, mittel] Doppel-URL-Encoding des `path`-Feldes in `ocs::create_share` (Share mit Sonderzeichen schlägt fehl)

- **Datei/Funktion:** `src-tauri/src/nextcloud/ocs.rs:262-273`
  (`let encoded_path = encode_segments(rel_path); … req.form(fields)`) +
  `src-tauri/src/nextcloud/mod.rs:23-24` (`req.form(fields)`).
- **Problem:** `encode_segments` produziert bereits `%20`-Sequenzen; der
  form-url-encoded POST (`req.form`) encodiert `%` erneut zu `%25` und `/` zu
  `%2F`. PHP dekodiert einmal → der Server erhält wörtlich `My%20Folder` statt
  `My Folder` → OCS-Fehler („path not found") für alle Dateinamen mit
  Leerzeichen, Umlauten, `#`, `&`, `+`, `?`. Einfache Pfade ohne Sonderzeichen
  funktionieren zufällig.
- **Fix-Vorschlag:** Raw-Pfad (decoded) ins Formular geben; das Encoding
  übernimmt `req.form`. Ggf. einen Roundtrip-Test ergänzen.
- **Hinweis:** `webdav::list`/`get_file` sind korrekt, weil dort nur die URL
  (einmaliges Encoding) betroffen ist; nur das Form-Feld ist doppelt encoded.

### F5 — [Bug, minor] About-Tab zeigt hartkodierte Version „0.1.0"

- **Datei/Funktion:** `src/components/SettingsModal.vue:237`
  (`{{ t("version") }} 0.1.0`).
- **Problem:** Nach Versions-Bump zeigt das About-Fenster weiterhin 0.1.0.
- **Fix-Vorschlag:** Version aus Tauri holen, z. B.
  `@tauri-apps/api/app.getVersion()` (kein Backend-Command nötig) oder
  `UpdaterInfo.app_version` aus `check_update`.

### F6 — [Bug, minor] `load_accounts` verwirft still alle Konten, wenn FLUTCLOUD_URL fehlt/abweicht

- **Datei/Funktion:** `src-tauri/src/accounts.rs:84-94` (Filter über
  `flutcloud_url()`).
- **Problem:** Fehlt `FLUTCLOUD_URL` in der `.env` oder weicht die
  `instance_url` eines Kontos ab, erscheint eine leere Kontenliste ohne
  Erklärung („FlutCloud-only" ist gewollt, aber der Nutzer bekommt keinen
  Hinweis, dass/why Konten ausgeblendet wurden).
- **Fix-Vorschlag:** Fehlermeldung/Status an das Frontend durchreichen
  (z. B. im `accounts`-Store einen Hinweis anzeigen), statt still zu filtern.

### F7 — [Feature, v1-empfohlen] Kein automatischer Update-Check beim App-Start

- **Datei/Funktion:** `src-tauri/src/updater.rs` (`check_update` existiert),
  Frontend ruft ihn nur manuell in `SettingsModal.vue` (Check-Button).
- **Vorschlag:** Beim Start (App.vue onMounted) asynchron `check_update`
  aufrufen und bei neuer Version ein nicht-blockierendes Update-Banner
  anzeigen. Für v1.0.0 sinnvoll, damit Nutzer von Bugfix-Releases erfahren.

### F8 — [Feature/CI, minor] Signing/Notarisierung nur dokumentiert, nicht konfiguriert

- **Datei/Funktion:** `.github/workflows/release.yml:116-141`
  (`sign-and-notarize-macos`-Action mit Secrets-Fallback auf ad-hoc).
- **Problem:** Ohne gesetzte Secrets (`APPLE_*`, `SIGNING_*`) werden macOS-Bin
  ad-hoc signiert und Windows-Setup unsigniert gebaut — Kataloge & SmartScreen
  warnen. V1.5/V1.8 ist damit nur „dokumentiert", nicht umgesetzt.
- **Fix-Vorschlag:** Vor v1.0.0 entscheiden: Entweder Secrets hinterlegen oder
  im Release-Hinweis auf SmartScreen-Warnung hinweisen. Zusätzlich:
  `opencode.yml` nutzt `anomalyco/opencode/github@latest` (unpinned,
  Supply-Chain) — auf Tag pinnen (übrige Workflows pinnen bereits
  `opencode-ai@1.18.18`).

### F9 — [Hinweis] SHA-256-Verifikation (V1.5) greift nur, wenn GitHub den Asset-Digest liefert

- **Datei/Funktion:** `src-tauri/src/updater.rs:302-310` (`asset_sha256`).
- **Problem:** GitHub liefert `digest` nur für per **API** hochgeladene Assets
  (tauri-action nutzt `gh release upload` → i. d. R. vorhanden). Fehlt der
  Digest (z. B. Web-Upload), wird **ohne** Warnung ungeprüft installiert.
- **Fix-Vorschlag:** Mindestens ein `eprintln!`/Log „checksum unavailable,
  skipping verification", besser: eigenen `.sha256`-Anhang im Release-Workflow
  erzeugen und immer prüfen.

### F10 — [Hinweis] Sync: gleiche lokale Ordnernamen kollidieren beim remote_path

- **Datei/Funktion:** `src-tauri/src/commands.rs:618-633` (`sync_add`,
  remote_path = `/FlutLink/{name}`).
- **Problem:** Zwei verschiedene lokale Ordner mit gleichem Namen können nicht
  für denselben Account synchronisiert werden (Duplikat-Check). Gewollte
  Einschränkung, aber im UI-Fehltext nicht erklärt („Another sync folder of
  this account already targets …").
- **Vorschlag:** Für v1 ausreichend; Fehlermeldung im SyncPanel anzeigen
  (passiert bereits) und im i18n-Text um „(choose a different folder name)"
  ergänzen. Optional: remote_path aus lokalem Pfad-Hash eindeutig machen.
